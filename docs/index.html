When is LLM-generated SQL safe to trust?

A query that throws a syntax error is a visible failure. A query that runs cleanly and returns plausible but wrong numbers is an invisible one. This study measures how often each happens, and finds the invisible kind gets worse as models get better.

SummaryWhat the study found

Teams are letting language models write SQL against production warehouses. The usual process is to validate on a benchmark, pick the prompt that wins, and deploy it everywhere. This study asks whether that is safe.

Few-shot prompting did nothing that could be distinguished from noise. Across all three complexity tiers the lift was −2, 0, and +8 percentage points, and every one of those was non-significant after correction. A ten-question pilot had suggested few-shot nearly doubled accuracy on hard queries. At the full sample that collapsed. Pre-registration is the only reason this is written up as a null result instead of a discovery.

The pilot showed 33% to 67% on complex queries. The full run showed 60% to 68%, p = 1.00 after correction. Committing the hypothesis and the test to Git beforehand removed the option of building a story around the pilot.

Model size was the only lever that moved anything, and only on the hardest queries: +28 points, and nothing at all on the middle tier. But the most interesting result is not about accuracy. The most accurate variant in the study made errors that were 100% silent. Every single one executed without complaint and returned believable wrong numbers. The weakest model at least failed loudly some of the time.

Choosing a model by benchmark score selects for quieter failures, not necessarily fewer dangerous ones. A wrong number that arrives with an error message gets investigated. A wrong number that arrives looking correct goes into a dashboard.

Finding 1Better models fail more quietly

Silent failure means the generated query ran without error and returned the wrong rows.

The ordering is not perfectly monotonic, and it should not be over-read at four points. What is clear is the grouping: the two 70B variants are 95% and 100% silent, and the two 8B variants are 81% and 89%. Broken out by question difficulty rather than by variant, 82% of errors on complex questions were silent, 95% on simple ones, and 97% on the middle tier.

The mechanism is visible in the error taxonomy. Loud failures are almost entirely schema_error, meaning the model invented a table or column. Stronger models stop doing that, so what remains is subtly wrong logic that executes fine.

The strong model also stated 95% average confidence on the answers it got wrong, so nothing in its own output flags the problem either.

The hypothesis was that few-shot lift would differ across complexity tiers. It does not, because there is no lift anywhere to differ.

Not significant is not the same as zero. The complex-tier point estimate is positive and its interval reaches +22, so a real moderate effect there cannot be ruled out. At 50 questions per tier this study can only detect differences of roughly 14 to 27 points.

The model effect is a different story. Upgrading from the 8B to the 70B model produced +28 points on complex queries (95% CI [+14, +42], p = 0.0013) under zero-shot prompting, and +16 points (p = 0.039) under few-shot. Those are the only significant effects anywhere in the study. On the moderate tier the same upgrade produced exactly zero: every variant landed between 82% and 84%, which suggests whatever limits accuracy there is not something this design manipulates.

Finding 3Confidence is useless, agreement is not

The weakest variant reported an average confidence of 98.6% while being correct 76.7% of the time. Even the best-calibrated variant overstates itself by 6 points. All four remain between 87% and 96% confident on the answers they get wrong, so confidence carries almost no information about whether a specific query is right.

A signal that does work costs one extra cheap call: run two models and compare what their queries actually return.

None of these signals needs the correct answer, so all three are available in production. Noticing that two models disagree requires no ground truth, which is exactly what makes it deployable.

Reviewing only the 28% of queries where two models disagree on the executed result catches 84% of all errors, at a 16% false-alarm rate. Comparing query structure instead catches everything but flags three quarters of all output, which is too noisy to act on.

Finding 4Difficulty routing did not beat random

Reported as the negative result it is.

The predictor uses only features computable from the question text and the schema, before any SQL is generated. That constraint is what makes routing worthwhile at all, since a feature requiring a model call would defeat the purpose. A single feature, question length, scored AUC 0.724 and beat the six-feature model at 0.665. Schema size was pure noise at 0.507.

Generalisation was weak too. Holding out an entire tier dropped complex-tier prediction to chance (0.525). Holding out entire databases, which is the real production question, held at 0.670 across 93 folds.

Two things here are worth more than the routing number itself. The oracle reached 90.0% accuracy at 37% of the always-expensive cost, beating always-expensive on both axes, so real headroom exists and these features simply could not reach it. And cost and difficulty turn out to be driven by different things: question length predicts difficulty but not cost, while schema size predicts cost almost perfectly (r = 0.95) and difficulty not at all. Input tokens are 95% of spend because the schema is pasted into every prompt, so the thing that makes a query expensive is not the thing that makes it hard.

MethodHow the sample was built

Everything runs on Spider, the text-to-SQL benchmark that ships executable SQLite databases. Execution accuracy is impossible without them. Difficulty tiers come from Spider's own eval_hardness() function rather than from my judgement, so a reader cannot accuse me of drawing the boundaries to fit the conclusion.

Spider train and dev examples8,034
Labelled into three tiers by the official hardness function8,034
Seeded sample, capped at 3 questions per database159
Excluded: gold query returned zero rows−7
Excluded: broken gold SQL found by hand review−2
Analysed, 50 per tier across 93 databases150

The two hand-review exclusions both came from the same database and shared the same defect: a join condition comparing a column to itself, which silently produces a cartesian product, plus a select list that returned last names when the question asked for first names. Benchmarks contain broken ground truth, and including it would have measured that instead of the models.

Every gold query was executed before its question entered the sample. Twenty were read by hand for ambiguity. The train and test split was assigned before any feature engineering, with whole databases kept on one side so no schema appears in both.

Scoring

A generated query counts as correct when it executes and its result set matches the gold query's. Row order is ignored, column names and order are ignored, duplicate rows are preserved so DISTINCT remains a real difference, and floats are rounded to four decimal places. There is no model acting as judge; correctness is a comparison of two result sets.

Generated SQL is untrusted input, so every query ran against a read-only copy of the database with a 30 second timeout and a 10,000 row cap. The cap earned its place: one query added a spurious join and tried to return more rows than that.

Validated against the official Spider scorer on 30 predictions: 18 of 19 agreed where both could score. The one disagreement is a spurious match, two structurally different queries that both happened to return 12. The official parser could not score 11 of the 30 at all; the executable scorer handled every one.

Statistics

The primary comparison uses McNemar's exact test, which is the correct test for paired binary outcomes and looks only at the questions where two variants disagree. A paired t-test on binary data is the standard mistake here and was avoided. Confidence intervals come from 10,000 bootstrap resamples of the questions, which preserves the pairing. The three primary comparisons carry a Benjamini Hochberg correction. Everything else is labelled exploratory and reported uncorrected.

At temperature 0 the outcome was identical across three pilot replicates in all 40 cells, so the full run uses one replicate per cell. The whole experiment is 680 successful calls costing $0.19 at list prices, and nothing at all in practice, since both models run on a free tier.

RecommendationWhat to actually do

  1. Spend on the model, not the prompt, and only where it pays. The upgrade bought 28 points on complex queries and nothing on moderate ones. Few-shot bought nothing anywhere.
  2. Never gate on self-reported confidence. A model claiming 99% certainty was wrong 23% of the time and stayed roughly 95% confident on its own mistakes.
  3. Do gate on cross-model disagreement. Two cheap models, compare the executed results, send disagreements to review. That is 28% reviewed for 84% of errors caught.
  4. Assume wrong answers will look right. Between 82% and 97% of errors executed cleanly, so guardrails belong on results, meaning row-count sanity checks, join fan-out checks, and reconciliation against known totals, rather than on error handling.
  5. Check a length-only baseline before building a difficulty router. Mine lost to it, and both lost to random.

LimitationsWhat bounds these claims

Benchmark contamination
Spider is public and predates these models' training cutoffs, so absolute accuracies are probably optimistic. It affects all four variants equally, which makes the comparisons more trustworthy than the raw numbers.
Underpowered for small effects
The minimum detectable effect at 50 questions per tier is roughly 14 to 27 points. A real but moderate few-shot benefit would not have been detected.
Complexity is tangled with length and schema size
Harder tiers came from larger databases and longer questions, so the complexity effect cannot be fully separated from a context-length effect.
Single-instance execution accuracy
Two different queries can return the same values by coincidence and both be scored correct. The cross-check found exactly one such case. Test-suite evaluation across many fuzzed databases would fix it and was out of scope.
The moderate tier tells us nothing
All four variants landed between 82% and 84%, so neither factor in this design moves it.
One model family, list-price costs
Both models are Llama variants from one provider, so the model effect means size within a family rather than a comparison between vendors. Actual spend was zero on a free tier.

ReproducingRunning it yourself

Every figure on this page regenerates from committed CSVs, so no database access is needed to check the numbers behind them. 

pip install -r requirements.txt && pip install -e .
python scripts/make_figures.py      # figures, from results/*.csv
python scripts/analyze_primary.py   # McNemar, bootstrap, BH
python scripts/analyze_calibration.py
python scripts/simulate_routing.py

Reproducing the experiment end to end additionally needs a Groq key and a Postgres connection string. Generation is cached and resumable, so an interrupted run costs nothing to restart, and re-scoring is always free because executions are stored separately from generations.
