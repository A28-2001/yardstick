SAMPLE

Difficulty tiers come from Spider's own hardness function, not my judgement, so the boundaries cannot be accused of fitting the conclusion. Every gold query was executed before its question entered the sample.

8,034  Spider train + dev examples
8,034  labelled into three tiers by the official hardness function
  159  seeded sample, capped at 3 questions per database
   -7  excluded, gold query returned zero rows
   -2  excluded, broken gold SQL found by hand review
  150  analysed, 50 per tier across 93 databases

The two hand-review exclusions shared a defect: a join condition comparing a column to itself, which silently produces a cartesian product. Benchmarks contain broken ground truth. Including it measures that instead of the models.

RESULT / SILENT FAILURE

Every error the most accurate model made was invisible. All 17 ran clean and returned wrong numbers.

QuestionWhich job titles correspond to jobs with salaries over 9000?
Gold
SELECT job_title FROM jobs WHERE min_salary > 9000
3 rows
70B zero-shot
SELECT JOB_TITLE FROM jobs WHERE MAX_SALARY > 9000
10 rows, stated confidence 1.00

Valid SQL, right table, real job titles, no error, wrong question answered. One word.

Both large-model variants sit at 95 and 100 percent, both small ones at 81 and 89. By difficulty: 82 percent silent on complex, 95 on simple, 97 in the middle. The strong model reported 95 percent average confidence on answers it got wrong.

RESULT / PROMPT AND MODEL

Few-shot prompting produced no significant gain at any tier. Model size did, and only on hard queries.

$ python scripts/analyze_primary.py
  complex (n=50 paired)
    V1 acc=0.600  V2 acc=0.680  diff=+8.0 pts  95% CI [-6.0, +22.0]
    McNemar exact p = 0.4240

Benjamini-Hochberg FDR across the primary comparisons:
  simple    adj p=1.0000  not significant
  moderate  adj p=1.0000  not significant
  complex   adj p=1.0000  not significant

A ten-question pilot had suggested few-shot nearly doubled accuracy on hard queries. At the full sample it vanished. Pre-registration is why this is a null result rather than a discovery.

8B to 70B bought 28 points on complex queries (p = 0.0013) and zero in the middle tier, where every variant landed between 0.82 and 0.84. Those are the only significant effects in the study.

RESULT / ROUTING FAILED

Question length alone beat my six-feature difficulty model. Both were matched by random routing.

Predictor AUC 0.665. Question length alone 0.724. Schema size 0.507, which is noise. Routing kept 88.7 percent of the expensive model's accuracy at 28 percent of its cost, and random routing at the same budget scored identically.

Two things matter more than the failure. The oracle beat always-expensive on both accuracy and cost, so the headroom is real. And cost and difficulty are unrelated: question length predicts difficulty, schema size predicts cost at r = 0.95 and difficulty not at all. Input tokens are 95 percent of spend because the schema goes into every prompt.

CONSTRAINT HIT

The 70B model has a hard daily token ceiling on the free tier. The run hit it.

$ python scripts/run_experiment.py --variant V4 --tier complex
Error code: 429 Rate limit reached for `llama-3.3-70b-versatile`
on tokens per day (TPD): Limit 100000, Used 99060, Requested 1048

Generated 165, skipped(cached) 19, failed 16.

Generation writes to Postgres after every call and the resume logic treats a failed call as pending rather than done, so the run continued the next day and completed all 600 cells at zero re-cost.

RECOMMENDATION

Spend on the model, not the prompt, and only on hard queries. Never gate on self-reported confidence. Gate on two models disagreeing. Assume wrong answers will look right, because 82 to 97 percent of them did, and put guardrails on results rather than error handling: row-count sanity, join fan-out, reconciliation against totals you already know. Check a length-only baseline before building a difficulty router.

Limits. Spider is public and may sit in training data, so absolute accuracies are probably optimistic, though all four variants are affected equally. At 50 questions per tier this detects effects of roughly 14 to 27 points and no smaller. Complexity is tangled with question length and schema size. Two different queries can return identical values by coincidence and both score correct; the cross-check found one. Both models are Llama variants, so the model effect means size within a family. Nothing was deployed.
